# ADR-003: Selection of Streaming ASR Runtime and Model Family

**Status:** Accepted  
**Date:** 2026-09-01  
**Deciders:** Core Engineering Team  
**Consulted:** Stage S2 Empirical Benchmark Report  

---

## 1. Context and Problem Statement

For `youtube-live-translate`, the Automatic Speech Recognition (ASR) subsystem is the initial stage of the realtime processing pipeline. The choice of ASR engine directly dictates:
1. **Time to First Transcript (TTFT):** The baseline latency before translation can begin.
2. **Partial Hypothesis Stability:** Whether provisional translations will thrash/flicker violently or progressively stabilize.
3. **Resource Footprint:** Memory and CPU budget remaining on consumer laptops for downstream Machine Translation (MT).
4. **Distribution Feasibility:** Whether the runtime can be compiled into a lean native binary (Rust/C++) without bundling a heavy Python runtime or CUDA stack.

---

## 2. Decision Drivers

* **Low Perceived Latency:** Must achieve $\text{TTFT} < 300\text{ ms}$ on consumer CPU hardware.
* **Monotonic Partial Stream:** Must emit stable prefix tokens to prevent downstream translation thrashing.
* **High Efficiency:** Must maintain $\text{RTF} \ll 1.0$ (target $< 0.10$) so that 4 CPU cores are never saturated.
* **Zero Mandatory Cloud Calls:** Pure local-first execution.
* **Packaging Simplicity:** Deployable via Native Messaging host with minimal memory footprint.

---

## 3. Considered Options

* **Option 1: Sherpa-ONNX (Streaming Zipformer / Emformer Transducer)**
* **Option 2: Faster-Whisper / whisper.cpp (Incremental Sliding-Window Decoder)**
* **Option 3: Commercial Cloud ASR (Google Cloud Speech, Whisper API, etc.)** — *Rejected per Architecture Invariant I2 (Local AI Runtime Mandatory)*.

---

## 4. Empirical Evaluation Summary (Stage S2 Benchmark)

| Evaluation Dimension | Sherpa-ONNX (Zipformer) | Faster-Whisper (Sliding-Window) |
| :--- | :--- | :--- |
| **Streaming Latency (TTFT)** | **$120 - 250\text{ ms}$** | $550 - 1200\text{ ms}$ |
| **Real-Time Factor (RTF)** | **$0.04 - 0.08$** (CPU) | $0.25 - 0.55$ (CPU) |
| **Partial Stability (Revisions)** | **$0$ destructive revisions** | $8 - 24$ revisions / sentence |
| **Stable Prefix Ratio (SPR)** | **$1.00$** (Pure monotonic) | $0.62 - 0.78$ (Frequent word mutation) |
| **Memory Footprint** | **$120 - 260\text{ MB}$** | $450 - 800\text{ MB}$ |
| **Native C++/Rust Embeddability**| **Excellent** (Native C-API, zero Python) | Moderate (CTranslate2 / ggml C++) |

---

## 5. Decision Outcome

**Chosen Decision:** **Option 1 (Sherpa-ONNX Streaming Zipformer)** as the **Primary Realtime Hot-Path Engine**.

**Secondary Role:** **Option 2 (Faster-Whisper)** is designated as **Cold-Path / Offline Fallback** (for full-sentence post-correction, offline transcript extraction, or fallback when specialized vocabulary requires Whisper's massive parameter scale).

### 5.1 Rationale
1. **True Frame-Synchronous Streaming:** Zipformer's transducer architecture processes audio incrementally frame-by-frame with $O(N)$ linear complexity, completely avoiding the $O(N^2)$ quadratic re-decoding bottleneck of sliding-window Whisper.
2. **Zero-Flicker Monotonicity:** Sherpa-ONNX yields a perfect $1.00$ Stable Prefix Ratio. This is essential for the Progressive Translation engine (Stage S4), allowing the MT layer to translate fixed prefixes once and only revise the active suffix.
3. **Packaging Advantage:** Sherpa-ONNX provides clean static C++ and Rust bindings (`sherpa-rs`), allowing the native host to be distributed as a compact single-binary installer ($< 30\text{MB}$ plus model weights) without Python or PyTorch dependencies.

---

## 6. Consequences & Next Steps

### Positive
- Guarantees sub-300ms ASR latency on modern x86_64 / ARM64 client CPUs.
- Leaves $>80\%$ of CPU budget available for Local Machine Translation (Marian / NLLB).
- Downstream translation algorithms can leverage monotonic stable prefixes directly.

### Negative / Mitigations
- Multilingual Zipformer models require separate language tokenizers or multilingual checkpoints (e.g. `ar_en_id_ja_ru_th_vi_zh`).
- *Mitigation:* The model manager (Stage S9) will download language-specific quantized Zipformer packages on-demand based on user preference.

### Immediate Action for Stage S3
Proceed to **Stage S3: Local Machine Translation (MT) Feasibility** to benchmark candidate local MT models (**Marian / OPUS-MT** vs. **NLLB-200 quantized**) on the text transcripts generated by the selected Zipformer engine.
